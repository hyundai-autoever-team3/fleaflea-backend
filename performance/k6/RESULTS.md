# 로컬 도감 목록 성능 측정

## 조건

- Windows 로컬 백엔드, PostgreSQL 16 Docker 컨테이너
- API: `GET /api/v1/members/me/collection-items?page=0&size=20`
- k6 2.2.0, VU 10명, 요청 간 대기 1초
- 인증된 로컬 테스트 계정 사용, 이미지 키는 NULL

| 도감 데이터 | 상태 | 시간 | 요청 수 | p95 | 실패율 |
| ---: | --- | ---: | ---: | ---: | ---: |
| 500건 | 인덱스 전 | 2분 | 1,163 | 70.01ms | 0% |
| 50,000건 | 인덱스 전 | 1분 | 549 | 136.96ms | 0% |
| 50,000건 | 인덱스 후 | 1분 | 590 | 27.15ms | 0% |

50,000건에서 p95가 약 80% 감소했습니다. 이 수치는 해당 로컬 환경의 동일 데이터와 설정에서 얻은 결과입니다. 1초 대기와 VU 10명 때문에 요청률이 약 10건/초로 제한되어 있으며, 이 결과만으로 서버 최대 처리량을 판단할 수 없습니다.

## 확인한 병목과 변경

인덱스 전 PostgreSQL 실행 계획은 도감 목록 첫 페이지를 구할 때 50,000건을 순차 조회하고 정렬했습니다. `EXPLAIN (ANALYZE, BUFFERS)`에서 약 15.43ms였습니다.

`V8__index_collection_item_lists.sql`에서 `(member_id, created_at DESC)`와 공개 목록용 `(member_id, is_public, created_at DESC)` 인덱스를 추가했습니다. 같은 첫 페이지 조회 계획은 인덱스로 필요한 20건을 읽었고 DB 실행 시간은 약 0.07ms였습니다. 앱 재시작 후 Flyway V8 적용과 health `UP`을 확인했습니다.

## 범위

도감 목록 조회를 실제 부하 측정하고 개선했습니다. 다른 조회 경로도 로컬 10 VU, 30초, 요청 간 1초 대기 조건으로 실행했습니다. 실패율은 모두 0%였습니다.

| API | 테스트 데이터 | p95 |
| --- | --- | ---: |
| 회원 도감 목록 | 도감 아이템 50,000건 | 160.73ms |
| 도감 상세 | 도감 아이템 1건 | 39.67ms |
| 플리마켓 목록 | 참가한 마켓 100건 | 1,579.74ms |
| 플리마켓 상세 | 마켓 1건 | 544.05ms |
| 플리마켓 참여자 목록 | 참가자 1명 | 278.22ms |
| 도감 거래 상세 | 거래 요청 1건 | 1,318.47ms |

플리마켓 목록을 같은 조건으로 다시 실행했을 때 p95는 691.27ms였습니다. 해당 SQL의 DB 실행 계획은 100건 조회에 약 4.33ms였으므로, 현재 결과만으로 DB 인덱스를 병목 원인이라고 단정할 수 없습니다. 이 경로와 도감 거래 상세의 긴 응답시간은 앱과 로컬 Docker 환경을 분리해 추가 관측할 필요가 있습니다.

도감 거래 상태 변경 시나리오는 3 VU, 30초, 서로 다른 아이템 81개를 사용했습니다. 생성·수락·완료·거절·취소 요청 189건이 모두 예상 상태 코드였고, 전체 p95는 110.07ms, 실패율은 0%였습니다. DB에서는 완료·거절·취소가 각각 29건으로 확인됐습니다. 이 수치는 서로 다른 동작이 섞인 전체 HTTP 지표이므로 동작별 성능 판단에는 각 요청의 `name` 태그를 분리해 다시 측정해야 합니다.

이미지 업로드가 필요한 도감 아이템·플리마켓 생성·수정 API는 이 로컬 시나리오에 포함하지 않았습니다.
