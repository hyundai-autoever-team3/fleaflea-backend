# 상품 목록 조회 성능 개선 결과

측정 방법과 실행 절차는 `ITEM-PERFORMANCE.md`에 있다.

## 측정 조건

- Windows 로컬, 백엔드 `bootRun -Pperf`(JDK 25), `performance/compose.yml`의 PostgreSQL 16, k6 v2.2.0을 같은 PC에서 실행
- 데이터: 상품 49,750건, 플리마켓 100개, 회원 1,002명. 측정 대상은 상품 3,000건인 대형 마켓
- HTTP: 10 VU, 1분, 요청 간 1초 대기. 네 API를 번갈아 3회 실행하고 p95의 중앙값을 쓴다
- DB: `explain-items.sql` 두 번째 실행 결과, 앱이 받은 쿼리 시간은 `pg_stat_statements`

## 변경 내용

| 단계 | 변경 |
| --- | --- |
| 1단계 | `items(market_id, created_at DESC, item_id DESC)` 인덱스 추가 (V10) |
| 2단계 | 검색 조건을 QueryDSL 동적 쿼리로 변경, 값이 있는 조건만 SQL에 포함 |

두 단계를 따로 적용하고 각각 측정했다. 함께 적용하면 실행 계획 선택에 서로 영향을 주어 효과의 출처를 나눌 수 없다.

## DB 실행 시간

실행 계획 기준.

| 쿼리 | Baseline | 1단계 | 2단계 |
| --- | ---: | ---: | ---: |
| 목록, 대형 마켓 첫 페이지 | 4.93ms | 0.043ms | 0.081ms |
| 목록, 소형 마켓(250건) | 2.63ms | 0.055ms | 0.048ms |
| 목록, 거래 방식 + 상태 필터 | 3.80ms | 0.27ms | 0.15ms |
| 목록, 검색어 `rare` | 3.20ms | 3.22ms | 2.57ms |
| 목록, 50번째 페이지 | 6.63ms | 3.39ms | 3.33ms |
| count, 필터 없음 | 3.53ms | 2.01ms | 0.37ms |
| count, 필터 | 3.38ms | 1.35ms | 0.98ms |
| generic plan 목록 / count | 9.34 / 5.92ms | 4.42 / 2.45ms | 0.04 / 0.42ms |

앱이 받은 쿼리 시간(`pg_stat_statements`, 필터 없는 목록 기준).

| 쿼리 | 1단계 | 2단계 |
| --- | ---: | ---: |
| count | 3.49ms | 0.337ms |
| 목록 | 0.058ms | 0.067ms |
| 마켓 존재 확인 | 0.022ms | 0.022ms |
| 참여자 확인 | 0.014ms | 0.014ms |

목록 요청 한 번의 DB 시간은 Baseline 실행 계획 기준 약 8.5ms에서 2단계 앱 기준 약 0.4ms가 됐다.

Baseline은 필터와 관계없이 테이블 전체(약 9.3MB)를 목록과 count가 각각 읽고 정렬했다. 상품 250건인 마켓도 5만 건을 모두 읽었다. 1단계는 인덱스 순서로 20건만 읽고, 2단계는 필터 없는 count가 인덱스만 읽는다(Index Only Scan).

## 함께 바뀐 동작

검색어가 없을 때 `lower(title) LIKE '%%'` 조건이 사라지면서, 상품명이 NULL인 상품이 목록에 포함된다. 이전에는 이 조건 때문에 제외되었다. 회귀 테스트에 이 동작을 확인하는 테스트를 추가했다.

## 측정의 한계

- 로컬 기준이다. 운영은 Nginx와 TLS를 거치고 DB가 같은 인스턴스에서 CPU를 나눠 쓰므로 절대값이 다르다.
- p99는 기록하지 않았다. 회차당 요청이 약 590건이라 p99가 요청 몇 개에 흔들린다(회차별 최댓값 21.3~61.4ms). 비교하려면 `-Duration 5m` 이상으로 재야 한다.
