## 이번에는 DB 락을 따로 봤다

[앞선 비교](https://github.com/hyundai-autoever-team3/fleaflea-backend/wiki/같은-마켓에-몰린-요청은-얼마나-기다릴까)는 일반 조회와 Redis+DB 락을 비교했다. 변경 유실을 막는 건 확인했지만, 두 락을 함께 추가했으니 어느 쪽이 변경을 지킨 건지는 나눠 볼 수 없었다. [#186](https://github.com/hyundai-autoever-team3/fleaflea-backend/issues/186)에서는 PostgreSQL 비관적 락 단독 대조군을 추가했다.

Redisson 도입 자체를 다시 결정하는 시험은 아니다. 현재 마켓 수정에서 DB 락에 Redisson을 더했을 때 값 보존과 지연이 어떻게 달라지는지 확인하고 싶었다. 운영 서버의 락은 바꾸지 않고 별도 테스트 VM에서만 실행했다.

## 같은 코드에서 수정 경로만 바꿨다

기준 커밋은 `efc15a702930afc2f7577656829e9161ac9611b7`이다. 마켓 수정의 분산 락 적용 여부와 행 조회 방식만 바꿔 세 실행 파일을 만들었다. 일반 조회·DB 락 단독 버전도 기존 계측 어노테이션은 남겨 실행 시간 계측 대상이 달라지지 않게 했다. 트랜잭션 경계는 유지했다.

| 버전 | 마켓 수정의 분산 락 | DB 조회 |
| --- | --- | --- |
| 일반 조회 | 제외 | 일반 조회 |
| DB 락 단독 | 제외 | PESSIMISTIC_WRITE |
| Redisson+DB | 유지 | PESSIMISTIC_WRITE |

GCP 서울의 e2-standard-2 두 대를 사용했다. 한 대에는 앱 두 개와 PostgreSQL 16.15·Redis 7.4.11·MinIO를 두고, 나머지 한 대에서 k6를 실행했다. 앱별 CPU 1개·메모리 1 GiB, JVM Xms256m/Xmx768m, Temurin 25.0.4.1+1로 맞췄다. OpenTelemetry 에이전트는 제외했다.

기존 합성 계정으로 이미지 없는 마켓 21개를 만들고 DB 스냅샷을 고정했다. 버전 전환 시 같은 스냅샷을 복원하고, 각 부하 조건 시작 전에는 대상 마켓의 제목과 설명을 같은 초기 값으로 맞췄다. 운영 데이터와 이미지 버킷은 사용하지 않았다.

## 200 응답을 받는 것과 값을 지키는 것은 달랐다

한 마켓의 제목과 설명을 두 요청으로 동시에 수정하고, 요청 두 개가 끝나면 다시 조회했다. 이 과정을 100쌍 반복했다. 쌍 사이에는 다음 수정이 끼어들지 않게 했다.

일반 조회 버전에서는 두 요청이 모두 성공해도 한쪽 변경이 사라졌다. 처음 읽은 엔티티의 다른 필드 값이 나중 저장에서 덮어써지는 경우다. 부하 중 HTTP 오류가 없다는 사실만으로 변경 보존을 확인할 수 없는 이유이기도 하다.

DB 트랜잭션과 겹치는 경우도 따로 봤다. SQL 트랜잭션이 설명을 바꾸고 행을 2초 동안 잡은 상태에서 실제 API로 제목을 수정했다. SQL 쪽을 커밋한 경우와 롤백한 경우를 나눠 최종 제목·설명을 확인했다. 애플리케이션 내부 예외를 주입한 시험은 아니다.

사전 시험 하나는 동시 수정 검증과 SQL 경합 검증이 같은 마켓을 동시에 사용해 값이 섞였다. 해당 결과는 제외하고 순서대로 다시 실행했다. 본 비교에서는 두 검증을 겹치지 않게 실행했다.

| 버전 | 수정 두 요청 모두 200 | 두 필드 보존 | 외부 COMMIT 후 보존 | 외부 ROLLBACK 후 보존 |
| --- | ---: | ---: | --- | --- |
| 일반 조회 | 100/100 | 48/100 | 덮어씀 | 보존 |
| DB 단독 | 100/100 | 100/100 | 보존 | 보존 |
| Redisson+DB | 100/100 | 100/100 | 보존 | 보존 |

일반 조회도 UPDATE를 저장할 때는 행 락을 기다렸다. 하지만 이미 읽은 오래된 설명을 엔티티에 담고 있어, 외부 트랜잭션의 커밋 뒤 그 값을 다시 저장했다. 조회부터 잠그는 것과 저장 시점에만 기다리는 것은 같지 않았다.

## 같은 요청률에서도 기다리는 시간은 달랐다

조회 80%·제목 수정 20%로 20·100 RPS를 보냈다. 한 마켓 집중과 20개 마켓 분산을 나누고, 조건마다 30초 예열 뒤 60초를 측정했다. 버전 순서는 1회 일반 조회→DB→Redisson+DB, 2회 DB→Redisson+DB→일반 조회, 3회 Redisson+DB→일반 조회→DB로 바꿨다.

본 측정은 36회, 요청은 129,625건, 성공 수정은 25,938건이었다. 본 측정 전체의 예약 누락은 0건이다. Redisson+DB의 집중 100 RPS 세 번째 실행에서만 409 응답 7건이 있었고, 본 측정의 500·503 응답은 없었다.

아래 p95·p99는 **각 실행의 성공 수정 지연을 구한 뒤 세 값의 중앙값**이다. 괄호는 실행별 p95의 최소~최대다. 전체 요청을 합쳐 다시 계산한 분위수가 아니며, 거절된 요청은 성공 수정 지연에서 제외하고 건수를 따로 남겼다.

| 요청 분포 | 목표 RPS | DB 단독 p95 ms (범위) | Redisson+DB p95 ms (범위) | DB 단독 p99 ms | Redisson+DB p99 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| 한 마켓 | 20 | 37.33 (33.41~41.83) | 53.95 (39.66~58.04) | 62.50 | 89.45 |
| 한 마켓 | 100 | 132.68 (98.33~176.97) | 898.94 (722.52~2444.25) | 261.83 | 1914.87 |
| 20개 마켓 | 20 | 18.80 (17.30~19.76) | 31.19 (30.77~34.14) | 27.98 | 44.39 |
| 20개 마켓 | 100 | 24.45 (19.16~26.01) | 38.44 (27.29~40.14) | 43.15 | 71.86 |

| 요청 분포 | 목표 RPS | 실측 요청/초, DB → Redisson+DB | 성공 수정/초, DB → Redisson+DB | 409 합계, DB / Redisson+DB |
| --- | ---: | ---: | ---: | ---: |
| 한 마켓 | 20 | 20.01 → 20.01 | 4.02 → 4.02 | 0 / 0 |
| 한 마켓 | 100 | 99.97 → 99.19 | 20.01 → 19.85 | 0 / 7 |
| 20개 마켓 | 20 | 20.01 → 20.00 | 4.02 → 4.00 | 0 / 0 |
| 20개 마켓 | 100 | 100.00 → 100.00 | 20.01 → 20.01 | 0 / 0 |

DB 락 단독은 이번 동시 수정과 커밋·롤백 경합에서 값을 지켰다. 이 요청률에서는 Redisson을 더해서 처리량이 늘거나 지연이 줄었다는 결과는 얻지 못했다. 특히 한 마켓에 몰린 조건에서는 성공 수정의 지연이 더 길었다. 일반 조회 버전은 변경 유실이 확인됐으므로 속도만 보고 선택할 대안으로 보지 않았다.

## 추가 대기는 어디에서 보였을까?

집중 100 RPS의 타이머를 나눠 봤다. 아래도 실행별 평균의 중앙값이다.

| 계측 구간 | DB 단독, ms | Redisson+DB, ms |
| --- | ---: | ---: |
| DB 잠금 조회 전체 | 7.40 | 6.05 |
| 수정 실행 전체 | 20.84 | 21.92 |
| Redis 락 획득 시도 | 해당 없음 | 160.84 |
| Redis 락 보유 | 해당 없음 | 22.02 |

DB 잠금 조회는 JDBC 통신과 쿼리 실행을 포함한 전체 시간이다. 순수 DB 락 대기 시간으로 읽으면 안 된다. Redis 획득 시간도 통신을 포함하고 성공·실패 시도를 함께 집계했다. 수정 실행 타이머는 Redis 획득 뒤부터 트랜잭션 종료까지를 본다. 서로 겹치는 구간이 있으므로 이 값들을 합쳐 HTTP 지연으로 계산하지 않았다.

두 앱의 수정 실행 건수 합계는 36개 측정 모두 HTTP 성공 수정 건수와 일치했다. 두 앱 모두 각 측정에서 실제 수정을 처리했다. DB 분산 100 RPS 첫 실행의 종료 스냅샷 하나는 수집이 빠져, 같은 구간의 주기 수집 원본에서 종료 건수가 1,201건으로 일치하는 샘플을 사용했다. 원본 시각은 UTC 01:33:31.885325이며 recovery.json에 출처를 남겼다.

## 자원과 해석 범위

본 측정 구간에서 관측한 앱 메모리는 컨테이너 제한의 최대 53.64%였다. 앱 한 인스턴스 CPU는 최대 98.82%(1코어 기준), PostgreSQL은 최대 24.13%(1코어 기준)였다. 부하 VM은 실행별 평균 CPU의 최댓값이 62.48%, 관측 최고가 87.63%(전체 코어 기준)였다. CPU의 분모가 달라 앱 수치와 부하 VM 수치를 그대로 더하지 않았다.

본 측정의 Hikari 대기는 앱별 최대 1개, PostgreSQL Lock wait event는 최대 4개 연결에서 관측됐다. 주기 샘플이므로 짧은 대기를 모두 포착한 값은 아니다. 본 측정의 예약 누락 0건과 자원 수치를 함께 남겼다.

이 결과는 이미지 없는 마켓의 제목·설명 수정, 조회 80%·수정 20%, 20·100 RPS라는 범위의 결과다. 같은 2 vCPU VM에서 앱과 DB·Redis가 자원을 공유했고 앱 CPU가 높아지는 구간도 있었다. 운영 서버의 용량으로 일반화하거나 이전 500 RPS 시험과 숫자를 합쳐 해석하지 않았다. 이미지 교체·마켓 삭제·참여와의 경합, Redis 장애, 더 높은 부하에서의 연결 풀 보호 효과까지 검증한 것은 아니다.

## 이번 결과로 남긴 판단

DB 락 단독도 이번 변경 보존 조건을 통과했다. 마켓 수정에서 Redisson 추가가 반드시 필요하다고 볼 근거는 얻지 못했고, 집중 부하에서는 추가 대기와 거절도 관측됐다. 다만 이 결과만으로 마켓의 다른 변경 경로나 도감의 분산 락까지 한꺼번에 제거하지는 않는다. 운영의 Redisson+DB 보호는 유지했고, 마켓 수정의 분산 락을 줄이는 변경은 이미지 교체와 다른 마켓 변경의 경합까지 확인하는 별도 PR에서 검토할 범위로 남긴다.

측정 종료 후 두 테스트 VM 모두 TERMINATED 상태를 확인했다. 각각 약 102분 사용해 승인한 2시간 안에 종료했다. 운영 서버·DB·Redis·버킷과 운영 코드에는 변경을 적용하지 않았다.
